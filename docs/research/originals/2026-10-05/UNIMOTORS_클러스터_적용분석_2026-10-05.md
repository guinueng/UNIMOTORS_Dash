# UNIMOTORS 클러스터 적용 분석

분석일: 2026-10-05. 포스터·재시작 복원·코드·상용차·규정을 연결한 연구 제안.

## 포스터에서 졸업연구로 이어지는 논리

처음 포스터의 장점은 유지할 자산, 단점은 검증할 요구사항, 개선방향은 비교할 해결책으로 바꾼다. 상용차 조사로 화면 구성 원리를 선택하고 대회 규정으로 판단 과제와 적용 조건을 정한다. 연구의 중심은 기존 로깅 플랫폼이 수집한 데이터를 운전자와 피트가 올바르게 이해하도록 만드는 것이다. [U01 p.1, 2·5~8절]

| 연결 단계 | 이미 가진 근거 | 졸업연구에서 남길 것 |
| --- | --- | --- |
| 현장 문제 | 속도 갱신 불만, 에너지 역산 필요, 공식 데이터 부재, 접점 용융이라는 팀 경험 | 문제별 실제 로그·운전자 진술·정비 기록. 당시 원인 설명과 검증된 원인을 구분. |
| 기존 성과 | 차량 로컬 수집·기록, VPN/LTE 전송, 피트의 GPS·BMS 분석 기반 | 기존 기능을 기준 시스템으로 고정하고 배포 버전·실측 성능을 기록. |
| 남은 간극 | 비검교정·BMS 의존·통신 비용·연산 자원 적정성에 대한 팀의 판단 | 정확도·지연·유효성·비용·자원 사용량의 측정 가능한 요구사항. |
| 화면 적용 | 상용차의 핵심 고정·콘텐츠 전환·최소 표시와 대회별 과제 | 속도와 경고 고정, 내구 예산·교체·팀 오더는 상황별 보조 정보로 비교. |
| 새 연구 기여 | 데이터 수집 기능의 존재와 운전자 판단 개선은 다른 증거가 필요 | 동일 입력의 기존/제안 UI 비교로 오답·반응 시간·오래된 값 오인 평가. |

### 통합 주제안

“전기 경주차에서 실시간 차량 데이터를 활용한 상황별 계기판 설계 및 평가”. 주요 질문은 목적별 정보 구성과 데이터 유효성 표시가 속도·내구 예산·고장 상태 판단을 개선하는가다. 계측·통신·연산 자원은 표시의 성립 조건으로 검증하고, 모든 기술을 한 번에 최적화했다는 주장을 목표로 삼지 않는다.

기존 구현 = 출발점 / 개선 설계 = 가설 / 비교 실험 = 새 기여. 포스터의 장점·단점은 팀이 기록한 주장이다. 아래의 정적 코드 관찰과 연구 제안을 같은 수준의 실험 결과로 표현하지 않는다.


## 포스터의 장점: 유지하면서 더 발전시킬 기반

| 장점 / 포스터 5절 | 적용 분석과의 연결 | 검증할 조건 |
| --- | --- | --- |
| VPN으로 비공인 IP 환경의 접속 제약 완화 | 차량–피트 연결 기반을 재사용. 로컬 운전자 표시와 서버 분석을 분리하고 연결 상태·마지막 수신 시각을 각각 표시. | 공인/비공인 IP 환경, 방화벽·망 변경·재연결·중계 경로의 실측 지연과 손실. “모든 망에서 가능”은 검증되지 않음. |
| 실시간 차량 상태를 보고 드라이버에게 오더 가능 | 피트 분석을 에너지 페이스·교체 준비 판단으로 연결. 계기판 수신 오더에는 발신원·발행 시각·유효기간·확인 상태를 제안. | 모니터링 후 사람의 오더와 계기판 안의 오더 수신 기능을 구분. 후자는 완성됐다고 볼 근거가 부족하므로 전달·중복·만료·운전자 인지 시험. |
| GPS와 배터리 데이터를 함께 분석 | 유효 랩별 소비·목표 Wh/lap·잔여 예산으로 번역. 운전자에게 필요한 최소 판단을 남기고 피트에는 상세 궤적·원시값을 유지. | V/I와 GPS의 시각 정렬, 랩 누락·BMS 지연·거리 오차·사용 가능 에너지 검증. 현재 used_wh의 운전자 SSE 전달 경로 추가 필요. [G01, G04] |

VPN의 연결 기능과 통신의 지연·가용성은 따로 검증한다. 비교용 예로 Tailscale 공식 문서는 UDP 차단·NAT 조건에 따른 직접/릴레이 연결 차이를 설명한다. 이는 팀의 VPN 종류를 확인한 결과가 아니라 포스터의 연결 장점을 조건부로 표현해야 한다는 근거다. [E01]

포스터 4절의 차량 내부 기록·연결 시 업로드 구조는 중요한 기반이다. 이를 운전자 로컬 판단과 사후 재현에 사용하되 기록 설정이 켜졌다는 사실만으로 저장 성공을 보장하지 않는다. 마지막 저장 성공·오류·누락을 상태 정보로 연결한다. [U01, G01]

경기 중 드라이버–팀원 통신은 허용된다. 팀 오더가 공식 깃발·교체 사인·재출발 지시를 대체하지 않도록 화면의 의미와 우선순위를 정한다. [K02 제17조 p.10, 제12조⑦ p.7]

| 기능 대비 과한 Pi Zero W 성능 | 포스터의 팀 판단이며 현 코드의 CPU·메모리·부팅·렌더링 실측 결과는 아님. | 실제 장치와 확장 기능을 고정해 자원·전력·부팅·주기 달성률 측정 후 유지/축소/교체 결정. | 소비전력·부팅·프레임 시간·주기 미달·저장/통신 부하. |

### 검교정과 UI 개선은 함께 필요하다

검교정된 센서도 값이 오래되면 잘못된 판단을 유도할 수 있다. 반대로 최신성 표시가 좋아도 센서 오차가 해결되는 것은 아니다. 정확도·최신성·가독성을 별도 요구사항으로 두고 최종 판단 과제에서 함께 평가한다. [U01, G01, G04]

BMS를 없애는 것이 개선 목표가 아니다. 비납산 축전지의 BMS는 기술규정 요구사항이다. 추가 홀센서는 독립 전류 비교 후보이며 전압 계측·영점·온도 영향·표본율·시각 동기화까지 갖춰야 에너지 비교에 사용할 수 있다. [K01 제9조③ p.3, 제10조⑤ p.5]

현재 소스와 마스터에는 Pi 이관·LCD 관련 계획도 있다. 포스터의 Zero W 설명을 현재 실차 보드의 확정 사양으로 간주하지 않는다. 경량화가 UI 반응·저장·통신 안정성을 희생하는지도 함께 비교한다. [U02, G02]


## 작년도 문제를 화면·계측 과제로 연결

포스터 2절의 네 가지 문제를 장단점 분석의 출발점으로 다시 연결했다. 상용차 사례는 화면 구성 선택의 근거이며 아래 문제를 이미 해결했다는 증거는 아니다. [U01 p.1]

| 팀의 기존 문제 | 지금 적용할 과제 | 상용차 원리 / 평가 |
| --- | --- | --- |
| 휴대전화 속도계 1Hz에 대한 불만 | GPS 원시 수집, GPS state, SSE, 렌더링을 분리해 전체 지연 측정. 큰 속도·단위를 고정하고 최신성 표시. | TT/MX-5의 주행 핵심 고정 [P01, T04]. 속도 변화 판독의 오답·응답 시간·지연 비교. |
| 배터리 사용량·거리 역산 필요 | 유효 누적 Wh를 운전자 경로에 연결. 내구에는 목표 대비 Wh/lap·남은 경기 예산. 학습 부족·누락은 명시. | BMW의 콘텐츠 분리·IONIQ 5 N의 목적별 성능 정보 [T01, T03]. 소비 예산 판단 비교. |
| 공식 미터 데이터 부재로 규정 충족 확인 어려움 | 팀 계측 정확도·빠른 과도 응답 비교. 화면에는 참고 출력·전압과 유효성. 공식 미터/판정과 팀 데이터를 구분. | BYD의 정보 상태 구분 [P12]. 낮은 화면 평균·오래된 값으로 제한 준수를 오인하는지 평가. |
| 킬스위치 접점 용융 경험 | 체결·전류 경로·보호 장치의 전장 원인 검토. 검출 가능한 신호·센서 위치를 정의하고 경고 의미·수신 실패를 구분. | 고정 경고·색 외 상태명 [P12, 연구 제안]. 실제 검출 근거 없는 “접점 과열” 경고를 만들지 않음. |

현재 GPS 원시 데이터는 포스터에서 10Hz로 설명되지만 GPS state 갱신 설정은 1초다. 따라서 작년의 1Hz 불만이 새 플랫폼에서 완전히 해결됐다고 주장할 수 없다. BMS는 별도 폴링 경로에서 갱신되며 SSE 전송은 0.5초 설정이다. 실제 표시 지연을 따로 확인한다. [U01, G01]

제동검사에서 공식 속도계와 비교할 수 있다는 규정은 속도 표시 검증에 활용한다. 출력·전압의 100ms/500ms 기준은 UI 애니메이션 개선과 다른 계측·제어 요구다. [K02 제6조⑤ p.3, K01 제10조⑤ p.5]

BMS 팩 전압·전류·온도만으로 접점의 국부 발열을 조기에 감지할 수 있다고 단정하지 않는다. 포스터 사진은 팀 경험을 보여 주지만 고장 탐지 성능을 입증하는 시험 자료는 아니다.

### 포스터 8절의 활용 방향은 단계별로 발전

팀 경주 전략 지원은 검증된 랩 소비·예산과 피트의 페이스·교체 준비부터 시작한다. 규정 안에서 완주와 기록을 함께 판단하는 도구로 평가한다. 예산 부족 예측이 실제 완주 성능을 개선했다는 주장은 별도 경기·실험 증거가 필요하다.

공식 에너지미터의 실시간 판정 보조는 주최 측과의 후속 협력 후보다. 정확도·표본율·데이터 무결성·공식 인터페이스·판정 책임·검증 시간 절감이 확인되어야 한다. 팀 계기판을 공식 장치로 승인받았거나 공식 미터를 변경할 권한이 있다는 뜻은 아니다. [K01 제10조⑤ p.5]

AI 전략은 유효한 학습 데이터, 비교할 단순 예산 기준, 예측 오차와 실패 처리가 갖춰진 뒤의 확장 후보다. 졸업연구의 초기 실험에는 사람이 이해할 수 있는 목표 대비 소비를 사용하고, AI가 없더라도 같은 핵심 판단을 수행할 수 있게 설계한다.

### 포스터의 단점을 실험 질문으로 바꾸기

| 연구 질문 | 같은 입력으로 비교할 조건 | 주요 지표 |
| --- | --- | --- |
| 상황별 구성이 내구 판단을 돕는가? | 현재 보조 정보 / 예산·유효 랩 중심 보조 정보 | 소비 예산 오답·응답 시간·시선 이탈 |
| 유효성 표시가 불확실한 값의 오인을 줄이는가? | 같은 배치에서 필드별 age·누락 표시 유/무 | BMS 지연·GPS 누락 판단, 잘못된 신뢰 |
| 팀의 지원을 짧은 오더로 이해할 수 있는가? | 수신 완료·만료·중복 메시지 시나리오 | 뜻 오인·늦은 오더 적용·행동 선택 시간 |

먼저 기준 시스템과 실제 장치를 고정하고 오차·지연·누락을 측정한다. 다음에는 기존 2×2 UI 비교를 활용해 배치와 유효성 효과를 분리한다. 오더 효과는 별도 파일럿으로 두어 변화 원인을 구별한다. 센서와 무선을 바꾸면 같은 로그의 UI 비교 결과와 별도로 보고한다.

제출 구조: 팀 문제·기존 플랫폼 → 포스터 장단점의 요구사항화 → 상용차 비교 → 규정 기반 경기 과제 → UI 설계 → 동일 로그 평가 → 결과·한계. 기존 시스템의 재사용 부분과 새로 구현·검증한 부분을 구분한다.

설계 목표는 신뢰할 수 있는 차량 데이터와 경기 맥락을 이용해 운전자·피트의 판단을 돕는 것이다. 이번 융합은 자료와 설계 가설을 연결한 작업이며 실차 성능·비용 절감·검차 합격·인지 개선을 입증한 결과는 아니다.


## 짧은 재시작 뒤 같은 경기를 이어가기

제안한 이전 데이터 복원은 우선 도입할 가치가 있는 기능이다. 차량 내부의 진행 기록을 영구 저장해 짧은 전원 중단·프로그램 재시작 뒤 같은 경기를 이어간다. 통신 중단 중 로그를 저장했다가 서버로 보내는 백필과는 역할이 다르다. 복원 효과와 허용 시간은 아직 검증되지 않았다.

| 현재 확인한 경로 | 재시작 시 의미 | 필요한 개선 |
| --- | --- | --- |
| used_wh / used_ah는 메모리 초기값 0 | 로그가 남아 있어도 프로그램이 누적값을 자동 복원하는 경로를 찾지 못함. | 확정 저장값에서 누적 소비 재개. 복원 근거·누락 구간 기록. [G01] |
| SESSION_ID는 시작 시 생성, 시계 점프 시 변경 | 하나의 경기가 여러 기술 세션으로 나뉘고 t_mono가 다시 시작될 수 있음. | 경기 ID와 수집 구간 ID 분리, 부팅/프로세스/시계 변경 이력 연결. |
| CSV 저장과 backfill.py 업로드 | 서버의 기록 복구이며 운전자 로컬 상태 복원과 다름. | 차량 복원과 서버 미전송 큐를 별도 관리. [G05~G07] |
| 최근 로그 3개 보관·주기 flush | 재부팅 반복 시 오래된 미전송 파일 삭제 가능. flush만으로 전원 차단 내구성 보장 불가. | 미전송 기록 보존과 확정 저장 상태 도입. [G01, E03] |

전기차에서 구동이 비활성화돼도 Pi/LCD 전원이 살아 있다면 재시작 복원은 필요 없고 상태 전환만 기록한다. Pi 전원이 끊기거나 수집 프로그램이 다시 시작된 경우에 복원 절차를 적용한다. 구동 READY를 표시하려면 실제 확인 가능한 구동 상태 신호가 필요하다.

### 검차 후 소프트웨어 변경에 대한 표현 조정

사제 계기판의 표시·로깅 소프트웨어 변경이 가능할 수 있다는 사용자 해석을 설계의 작업 가정으로 반영한다. 앞선 임의 업데이트 제한은 팀 운영 제안이었으며, 원문만으로 UI 수정 금지를 단정하지 않는다. 하드웨어·구동 한계·차단회로에 영향을 주는 변경과 구분해 버전·변경 내용을 기록한다. 변경 허용이 공식 확인됐다고 주장하지 않는다. [K01 제40조, K02 제4조]


## 복원할 기록과 다시 받아야 할 현재 값

| 데이터 | 복원 방침 | 이유 / 조건 |
| --- | --- | --- |
| 경기 ID·차량·배터리 사용 구간 | 유효한 같은 경기만 연결 | 차량·경기·배터리 교체/충전·종료 상태 확인. 현재 코드에 자동 배터리 식별이 있다고 가정하지 않음. |
| 누적 Wh/Ah | 마지막 확정 표본의 총량 복원 | 사용량의 정의·부호·계측 경로 일치. 전원 OFF 구간을 마지막 전류로 적분하지 않음. |
| 완료 랩·유효 거리 | 검증된 완료 기록 복원 | 현재 운전자 로컬 랩·거리 기능은 추가 설계 대상. 진행 중 랩은 중단/불완전 표시. |
| 화면·경기 프로파일 | 호환된 설정 복원 | 설정과 데이터 스키마 버전 확인. 새 경기 시작 선택 가능. |
| 속도·GPS fix·V/I·SOC·온도 | 초기에는 -- / 갱신 대기 | 과거 값을 현재 정상 값처럼 재사용하지 않음. 신선한 표본 수신 후 표시. |
| 경고·팀 오더 | 과거 이력은 복원, 현재 지시는 재확인 | 오더의 발생 시각·유효기간·취소 확인. 과거 경고의 소멸과 현재 정상은 다른 의미. |
| 적분 last_t·필터·전 랩 좌표 | 초기화 후 새 구간 생성 | 정지 구간 가짜 소비·급격한 가짜 G·출발선 가짜 통과 방지. |

초기 시험안은 “최근 확정 저장 시각에서 신뢰 가능한 현재 시각까지 5분 이내”다. 5분은 사용자 제안을 구체화한 시험값이며 규정·확정 최적값이 아니다. 같은 경기·종료되지 않음·동일한 배터리 사용 구간·유효한 저장본을 모두 만족할 때 자동 이어가기를 검토한다.

시간 미확정, 충전·교체 여부 불명, 긴 중단이면 후보 기록을 보존하고 정차 후 담당자가 이어가기/새 경기 시작을 선택한다. 5분 안이어도 충전·배터리 교체·다른 종목 시작이 있었다면 기존 에너지 예산을 자동 재사용하지 않는다.


## 복원 판단: 시간·표본·저장을 함께 설계

### 시계가 맞기 전에는 몇 분인지 알 수 없는 경우가 있다

현재 코드에는 RTC 없는 부팅과 GPS/NTP 시각 변경 대응이 있다. 동기화 전 time.time()만으로 5분을 판단하면 잘못 이어갈 수 있다. 같은 Linux 부팅의 프로그램 재시작은 부팅 ID와 같은 단조 시계의 경과를 사용할 수 있지만, 전원 재부팅 뒤에는 이전 monotonic 기준을 그대로 비교하지 않는다. 신뢰 시각 확보 또는 정차 확인이 필요하다. [G01, E06]

ID 제안: race_session_id는 경기 전체, segment_id는 재시작·계측 중단별 수집 구간, sample_id는 각 확정 표본이다. 부팅 ID·프로세스 ID·시계 변경은 메타데이터로 기록한다. 서버 집계도 전체 경기와 구간을 구별해야 재시작된 t_mono를 같은 연속 시간으로 오해하지 않는다.

| 확정 저장본의 항목 | 기능 |
| --- | --- |
| schema_version · generation · vehicle_id · race_session_id · battery_epoch | 호환성·차량·경기·배터리 사용 구간 확인 |
| segment_id · sample_id · used_wh · used_ah · 완료 랩/거리 | 기준 표본 뒤에서 소비와 진행 기록 재개 |
| saved_utc · time_quality · boot_id · monotonic_at_save | 같은 부팅 여부와 시간 판단 근거 |
| profile_version · ended · charging/change 확인 · gap 이력 | 새 경기·충전·종료·구성 변경을 구별 |

### 같은 표본 뒤에서 한 번만 재개하기

적분은 telemetry_snapshot() 조회 때마다 계산하는 방식에서 유효한 새 센서 표본 처리로 분리한다. 체크포인트와 마지막 반영 표본 ID를 같은 기준으로 확정한다. 복원 뒤 로컬 로그를 다시 읽는 경우 그 ID 이후의 확정 표본만 재처리하고 이미 합산한 소비를 더하지 않는다.

예: 저장된 872.4Wh → 30초 계측 중단 → 복원 → 새 유효 표본의 측정 소비 5.0Wh이면 877.4Wh로 표시하고 30초 누락을 함께 남긴다. 중단 구간 소비는 모르는 값이며 0 소비나 마지막 전류를 곱한 값으로 확정하지 않는다. 수치는 가상이다.

경기 시간·교체 타이머는 공식 기록과 분리한다. 신뢰 시각으로 기한을 복원한다면 전원 OFF 시간도 경과에 포함하며, 불확실하면 시간 확인 대기 상태를 사용한다. 타이머를 멈춰 공식 허용 시간이 늘어난 것처럼 보이지 않게 한다.


## 영구 저장과 재전송도 함께 개선

최소 구현 후보는 두 세대의 상태 파일과 CSV 유지다. 같은 파일시스템의 임시 파일을 쓰고 flush·fsync 후 원자적으로 교체하며, Linux의 디렉터리 동기화와 이전 확정본 복구를 검토한다. 확정 표본 ID·스키마·무결성·실제 로그와의 일치를 검사한다. 정상 종료 시 저장만으로 갑작스러운 전원 차단을 해결할 수는 없다. [E03]

기록·복원·미전송 큐를 함께 확장할 때는 로컬 SQLite의 트랜잭션 구조를 비교한다. WAL+FULL은 커밋 동기화를 강화하지만 NORMAL과의 지연·쓰기 비용을 실측해야 한다. 어느 방식도 불량 SD·OS/장치의 잘못된 동기화를 완전히 해결한다고 보장하지 않는다. [E04, E05]

| 현재 정적 관찰 | 개선 제안 |
| --- | --- |
| KEEP_FILES=3, 업로드 확인과 무관한 파일 삭제 [G01] | 미전송·활성 경기·복원 기준 로그 보존. 공간 경고와 명시적 보관 정책. 무한 보관 대신 용량 상한과 데이터 손실 상태 기록. |
| 서버 키는 summary(vehicle, ts), track(session, ts) [G06] | vehicle+segment+sequence 등 시각 보정에 독립적인 표본 ID. 같은 표본 재전송은 한 번만 반영. |
| /upload에서 track 일부 필드만 저장 [G06] | 누락 구간의 Wh·온도·경고 등 전체 스키마 복구를 설계. 궤적 백필 성공을 모든 분석값 복구와 혼동하지 않기. |
| 차량·업로드 코드에서 CSV split(",") 사용 [G05, G06] | 정식 CSV 파서·행별 검증·거부 이유·개수 기록. 따옴표·쉼표·잘린 마지막 행 시험. |
| WS live 전달과 DB 저장 확정의 시점이 다름 [G06] | 서버 커밋 완료 뒤 표본/범위 ACK. ACK 유실은 재시도하고 중복 반영을 막음. 차량 큐 삭제는 확인 뒤에 수행. |
| 저장소 타이머는 부팅 3분·이후 15분 [G07] | 기존 타이머는 예비 수단으로 두고 재연결 시 제한된 크기의 백필. 최신 경고·오더·표시 갱신을 과거 로그가 밀어내지 않도록 우선순위 설정. |

현재 소스가 실제 차량·서버 배포본과 같은지 먼저 확인한다. 위 내용은 정적 분석이며 실제 데이터 손실을 재현한 시험 결과가 아니다. 재전송된 누적 Wh는 동일 표본의 상태값으로 저장하고 수신할 때마다 합산하지 않는다.

## 운전자에게 보여 줄 복구 상태와 조작

### 복구는 배경에서 수행하고 핵심 정보는 즉시 제공

부팅 후 저장본 확인, 신선한 센서 수신, 피트 재연결을 병렬 진행하는 구조를 제안한다. 네트워크·GPS 시간 동기화·대량 백필 때문에 사용할 수 있는 로컬 정보까지 기다리지 않게 한다. 센서 값이 아직 없으면 --로 구별한다. 실제 부팅·첫 유효 값·UI 응답 시간은 측정해야 한다.

이어가기/새 경기·배터리 교체·랩 정정은 실제 물리 입력 또는 정차한 팀 담당자의 조작 방식을 정한다. 현재 터치·버튼이 설치돼 있다는 가정 없이 후보로 남긴다. 주행 중 확인을 강요하는 모달이 속도·경고를 가리지 않게 한다.

데이터 복원은 구동 재시동과 별개의 기능이다. 이전 READY를 복원해 AIR를 닫거나 스위치 복귀를 자동 출발로 바꾸지 않는다. 요구되는 안전 전원 차단을 우회하는 백업 전원을 이 분석에서 제안하지 않는다. [K01 제7조⑥, 제32조⑧]

### 필수 시나리오

정상 종료와 갑작스러운 전원 상실, 같은 부팅의 프로그램 재시작, 30초/3분/5분 경계/10분 중단, NTP/GPS 시계 점프, 잘린 저장본, 디스크 부족, 배터리 교체·충전·다른 경기 시작을 시험한다. 각 시간은 시험 입력이며 확정 복원 임계값이 아니다.

중단 후 서버 연결만 복구됐을 때, ACK가 유실됐을 때, 백필 도중 또 재부팅됐을 때, CSV에 쉼표·따옴표가 있을 때도 비교한다. 같은 표본 수·최종 누적·완료 랩·불완전 랩·누락 구간·보존 파일이 예상과 일치해야 한다. 현재 기본키와 새 ID 전환은 서버 데이터 호환성까지 검증한다.

주 지표는 복구까지 걸린 시간, 마지막 영구 저장 대비 손실 표본/Wh, 잘못 이어 붙인 경기 수, 중복 소비·중복 랩, 미전송 데이터 보존, UI 상태 오답이다. 저장·동기화 주기는 1~5초를 비교할 후보로 두고 저장 지연·쓰기량·UI 반응·실제 손실을 측정해 정한다.

짧은 재시작 복원 + 데이터 유효성 표시 + 내구 예산 판단을 우선 묶으면 포스터 장점의 지속성과 단점의 신뢰성 문제를 함께 다룰 수 있다. 복원이 미계측 소비를 복구한다거나 공식 기록을 보장한다고 주장하지 않는다. 이번 작업은 분석과 설계 제안이며 차량 코드 구현·배포·전원 시험은 수행하지 않았다.


## 대회 적용의 중심: 규정 준수와 완주 판단

상용차 조사에서 얻은 고정 정보·목적별 콘텐츠·유효성 피드백을 대회 과제에 맞춰 발전시킨다. 우선순위는 출력·전압 제한 및 물리 안전장치와의 양립, 그다음 경기별 판단과 완주 에너지 예산이다. 외관 테마는 그 위에서 비교한다. 이 절은 설계 분석이며 차량 소프트웨어 변경이나 검차 합격 결과가 아니다.

### 점수 구조가 말해 주는 목표

총 1,000점 중 보고서 200, 가속 100, 짐카나 150, 주행성능 150, 내구 400점이다. 내구는 완주 150점과 기록 성능 250점으로 구성되며 미완주는 DNF다. 따라서 소비량만 최소화하는 화면보다 제한을 지키며 완주 가능성과 페이스를 판단하게 하는 화면이 적합하다. 이 점수표를 별도의 EV 연비경진대회에 적용하지 않는다. [K02 별표1 p.11, 제12조⑤ p.6]

규정 문서의 참가팀 의무는 차량 요구사항으로 분석한다. 문서 속 제출·연락·조작 안내를 지금 실행하라는 사용자 지시로 취급하지 않는다. 원문 페이지 번호는 PDF의 1부터 센 페이지다.

| 포메이션 집계 | 공식 기록에 미포함. 제12조① p.6 | 랩 수를 기록에 포함. 핸드북 p.18 |
| 전압 | 58V. 기술 제9조② p.3 / 경기 제9~12조 | 핸드북 p.14~16·18은 59V 미만. 검차 시트 p.6 항목33은 최대 58V |
| 구체 코스 | 가속 70~100m. 주행성능 랩 수 사전 공지 | 가속 75m, 주행성능 12랩. 핸드북 p.14·16 |

모든 항목을 설정값으로 관리하고 출처·문서 버전·승인 근거를 저장한다. 전압은 확인 전 58V 이하를 바탕으로 여유를 검증하는 보수적 연구안으로 두되 59V 운용을 허가받았다고 주장하지 않는다. 랩·포메이션·교체·인원은 별도 확인이 필요하다.

기술 제39조는 번호 중복, 제32조②의 제56조⑤ 참조 및 경기규정의 일부 기술규정 참조는 편집 오류 가능성이 있다. 문서명·조문 제목·페이지를 함께 적고 위원회 해석을 기록한다.


## 10kW·전압 제한: UI가 맡을 수 있는 범위

기술 제10조⑤5(p.5)는 최대 출력 또는 전압을 연속 100ms 이상 초과하거나 각각의 500ms 이동 평균이 최대값을 넘으면 위반으로 본다. 공식 미터는 축전지 출력단을 측정한다. 경기 제9조⑥·제10조⑦·제11조⑬·제12조⑪도 미터 기준 DNF를 명시한다. 모터 정격이나 화면 평균이 낮다는 이유만으로 통과한다고 볼 수 없다. [K01, K02]

| 층 | 담당 기능 | 검증할 내용 |
| --- | --- | --- |
| 구동 제어 | 검증된 계측과 컨트롤러의 출력·전압 제한 | 측정 오차·과도 상승·제어 지연을 고려한 여유. 고정 전류 제한은 전압 변화에 따른 V×I 변화를 함께 확인. |
| 운전자 UI | 참고 출력·전압·최신성·접근 경고 | 제어 한계와 경고 임계값 구분. 경고 확인 버튼이 제한을 해제하거나 구동을 재개하지 않음. |
| 팀 로거 | 원시 시각·V/I·유효성·누락·이벤트 저장 | 정확한 시간 기반 500ms 창과 기준 계측 비교. 부호·회생·동기화된 V/I 표본의 의미 확인. |
| 공식 판정 | 주최 측 에너지미터와 운영위원회 | 팀 센서/UI가 공식 판정을 대체하지 않음. 공식 미터의 세부 사양·판정 설정 확인. |

### 현재 코드에서 부족한 부분

BMS 빠른 조회 설정은 약 0.33초, GPS state 갱신은 약 1초, SSE 전송은 약 0.5초다. BMS는 별도 폴링 경로에서 state를 갱신한다. 이는 코드 설정이며 실측 주기가 아니다. 조회 t=0·0.33초 사이의 t=0.12~0.24초 초과는 놓칠 수 있다. SSE만 빠르게 보내도 원본 계측 대역폭은 늘지 않는다. 현재 경로로 100ms 위반 탐지를 보장할 수 없다. [G01, G04]

9.5kW 등의 임의 값을 규정 기준으로 정하지 않는다. 계측 오차와 실제 과도 응답으로 제어 여유·UI 경고를 결정한다. 100ms 미만 펄스도 500ms 평균 조건에 걸릴 수 있으므로 “짧으면 허용”으로 분류하지 않는다. 초기 검증은 저장 로그·합성 파형 재생으로 수행한다.


## 경기별 콘텐츠: 같은 위치, 다른 판단 과제

기본·내구·정비라는 화면 구조에 가속/짐카나/주행성능/내구 경기 프로파일을 결합한다. 큰 속도, 단위, 경고, 데이터 상태는 같은 위치에 둔다. 경기·랩 수는 출발 전에 설정하고 주행 중 세부 설정 화면은 최소화한다. 아래 내용은 팀의 선택적 연구 제안이다.

| 경기 | 운전자에게 남길 정보 | 피트에서 분석할 정보 |
| --- | --- | --- |
| 가속 / 100점 | 속도·즉시 경고·참고 출력. 작은 출발 대기 상태. 주행 중 순위/그래프 최소화. | V/I 과도 변화·계측 지연·최고 출력·팀 참고 시간. 공식 기록은 트랜스폰더와 대조. [K02 제9조 p.3~4] |
| 짐카나 / 150점 | 속도·경고·데이터 정상 여부. 이동 경로·정지구역은 코스워크로 숙지. | 콘 접촉·코스 이탈·정지구역을 관찰 기록과 대조. GPS로 공식 벌점을 자동 확정하지 않음. [제10조 p.4~5] |
| 주행성능 / 150점 | 팀 추정 랩·출력·BMS 온도·원인별 경고. 전체 랩 수는 검증된 프로파일에서 읽음. | 랩별 소비·일관된 페이스·열 상태·실제 결과. 규정상 결과가 내구 출발순서에 연결됨. [제11조 p.5~6] |
| 내구 / 400점 | 팀 추정 남은 랩·최근/목표 Wh/lap·공식 교체 사인 확인·단계. | 사용 가능 에너지·보존량·교체 준비·랩 집계 오차. 과소비와 센서 끊김을 구분. [제12조 p.6~7] |

속도·출력·온도만으로 “안전” 또는 “검차 합격”을 표시하지 않는다. 모터 온도는 현재 확인한 데이터에 없으므로 BMS 최고온도와 구별한다. 라벨은 단순히 온도라고 쓰지 않고 측정 위치를 확인해 확정한다.

공식 시간 계측은 주최 측 트랜스폰더다. GPS 랩 수와 팀 타이머에는 “팀 추정”을 표시하고 공식 보드·판정과 수동 정정할 수 있게 한다. 트랜스폰더 이탈·불동작도 출발 전 점검 항목에 포함한다. [K01 제37~38조 p.22~23]


## 내구 에너지 예산을 운전 판단으로 바꾸기

### 최소 기능: 현재 가능한 누적 소비부터

현재 used_wh는 telemetry_snapshot()에서 계산되지만 운전자 SSE는 state를 보내므로 누적값이 자동으로 화면에 전달되지는 않는다. 유효한 동기 V/I 표본과 단조 증가하는 시간으로 적분하는 로컬 계산기를 먼저 만들고 UI·CSV·피트에 같은 결과를 전달하는 것을 제안한다. BMS 최신성 확인 없이 캐시를 적분하는 경로도 수정 대상이다. [G01, G04]

누적 순소비 Wh = Σ(V×I×실제 Δt)/3600. 회생 전류 부호, 에너지 계측 위치, 누락 구간을 정의한다. 누락을 0 소비로 채우지 않는다. 축전지 규격 58V·80Ah를 곱한 값을 실제 사용 가능 에너지라고 확정할 수 없다. 부하·온도·전압 차단 조건으로 사용 가능량을 검증한다. [K01 제9조② p.3]

### 예산은 경기 프로파일과 연결

목표 Wh/lap = (현재 사용 가능 잔여 Wh − 완주 보존량 Wh) / 남은 유효 경기 랩 수. 최근 정상 랩의 소비와 목표를 비교하고 추정 준비·누락·불확실성을 표시한다. 포메이션이 공식 집계에 포함되는지는 프로파일에 따르되 물리적으로 소비한 에너지는 항상 차감한다. 드라이버 교체에서도 배터리 누적 소비를 초기화하지 않는다.

| 상태 | 표시 제안 | 필요한 조건 |
| --- | --- | --- |
| 유효 랩 부족 | 추정 준비 중 / 누적 소비 | 최소 학습량은 실제 변동성으로 정하기 |
| 최근 소비 > 예산 | 목표 대비 차이 / 팀 페이스 협의 | 표시만으로 자동 토크 제한을 실행하지 않음 |
| BMS 지연 | 소비 추정 불가 / 누락 표시 | 전류를 마지막 값으로 계속 적분하지 않기 |
| GPS 랩 누락 | 팀 랩 미확정 / 피트 확인 | 수동 보정 이력·공식 계수와 비교 |

보존량과 경고 숫자는 로그·기준 계측·파일럿으로 정한다. 무선 서버가 끊겨도 차량 전원이 정상인 동안 로컬 계산을 유지한다. 안전 차단으로 전원이 꺼질 때에는 로깅 지속을 약속하지 않는다.


## 드라이버 교체: 공식 사인과 팀 준비를 연결

기본규정은 공식 교체 사인 수신 후 교체구역에 진입하고, 교체에 3분을 부여하며 초과분을 기록에 가산한다. 교체 후 출발 문제가 있을 때 재출발까지 최대 2분이 주어지고 불가하면 DNF다. 이 두 시간을 합쳐 누구에게나 5분 교체 시간을 주는 것으로 표시하지 않는다. [K02 제12조⑦1·3·6, p.7]

| 단계 | 클러스터 제안 | 팀이 확인할 것 |
| --- | --- | --- |
| 사인 전 | 교체 준비 상태만 표시 | 사전 준비 메시지는 공식 교체 사인과 구분 |
| 공식 사인 확인 | 교체구역 진입 안내 / 확인 시각 | 오피셜 지시·해당 차량 여부·현장 동선 |
| 정차·교체 | 참고 교체 타이머 / 드라이버 식별 | 시작·종료 기준은 공식 운영과 대조 |
| 교체 완료 | 드라이버 2 / 전체 소비 유지 | 벨트·장갑·물리 시작 절차는 실제로 확인 |
| 출발 문제 | 별도 재출발 상태 / 팀 참고 시간 | 2분 기준의 실제 기산 시점을 현장 확인 |

교체 인원은 문서 간 차이가 있으므로 공식 확인 전 고정 인원 규칙을 배포하지 않는다. 기본규정은 조끼 착용과 초과 인원 1명당 50점 감점을 명시한다. 허용 공구는 타이어 정비용이며 전동공구는 금지다. 계기판은 준비 확인을 지원하지만 인원·공구·벨트 상태를 센서 없이 자동 검증했다고 보여주지 않는다. [K02 제12조⑦4·5, p.7]

25랩 도달을 교체 사인으로 자동 대체하지 않는다. 피트가 현장 공식 사인을 확인해 팀 메시지로 전달한 경우에도 발신원은 TEAM으로 표시한다. 통신이 끊기면 화면 안내가 최신 공식 지시인지 알 수 없으므로 오피셜·현장 보드를 따른다.


## 경기 단계와 메시지의 수명

| 단계 | 표시 / 기록 원칙 | 전환 근거 |
| --- | --- | --- |
| READY | 경기명·설정 버전·센서 유효성·로그 성공 | 팀의 출발 전 확인 |
| FORMATION | 큰 속도·경고 유지, 에너지 소비 누적 | 현장 시작 확인 / 집계는 승인된 프로파일 |
| RACE | 경기별 보조 정보와 팀 추정 랩 | 공식 시작을 팀이 확인한 이벤트 |
| CHANGE | 정차 확인 후 교체 참고 타이머 | 오피셜 사인·구역 진입을 수동 확인 |
| COOLDOWN | 경고·한계 감시·기록 계속 | Finish 통과 후 코스 밖으로 나갈 때까지 |
| STOP / FAULT | 전원 정상 시 상태 구분·복구 후 이력 | 데이터·UI 오류와 물리 차단을 구분 |

경기 종료는 Finish Line이 아니라 경기장 밖으로 나가는 순간이다. 결승선 통과만으로 한계 감시나 규칙 안내를 종료하면 안 된다. 차단 회로 복귀도 UI 상태 전환만으로 재시동시키지 않는다. [K02 제14조 p.9, K01 제32조⑧ p.21]

### 팀 통신은 허용되지만 공식 신호를 대체하지 않는다

경기 제17조(p.10)는 드라이버–팀원 통신을 허용한다. 제안 메시지 필드는 ID, 경기/차량, 발신원, 내용, 발생·수신 시각, 유효기간, 수신 확인, 취소 이력이다. 오래된 오더 재전송·중복·순서 역전은 무효 또는 지연 상태로 처리한다. 수신 확인은 행동 완료나 공식 허가와 구분한다. [K02]

팀의 깃발 전달은 현장 관찰자의 입력에 의존한다. 황색은 감속·추월 금지, 적색은 중단이라는 핸드북 의미를 참고할 수 있지만 자동 영상 인식이나 GPS 위치만으로 공식 깃발을 확정하지 않는다. 세부 의미와 재개 절차는 공식 브리핑을 따른다. [K03 p.21]

스핀·차선 이탈 뒤 복귀에는 진행요원의 지시가 필요한 경우가 있고, 깃발 불복종에는 벌칙이 있다. UI는 “오피셜 지시 확인”을 보조한다. GPS 위치로 추월 허용·벌점 없음·차량 간격 5m 충족을 판정하지 않는다. [K02 제11조⑫·제12조⑩·제13조, p.6~8]


## 대회 화면 시안: 내구와 교체

800×480 기준 연구용 시안이다. 모든 숫자는 가상이다. 내구 화면의 HB 후보는 핸드북의 후보 설정을 뜻하며 적용 승인된 경기 설정이 아니다. 실제 구현 시 설정이 미확정이면 팀에 이를 명확히 표시한다.

내구 후보: 속도 고정, 팀 추정 랩과 소비 예산, 참고 V/I·데이터 나이. 공식 판정·교체 허가를 보장하지 않는 화면.

화면 시안은 통합 PDF 참조. 수치는 가상이며 실차 계측·공식 판정 결과가 아니다.

정차 교체 후보: 공식 사인 수동 확인과 기본규정의 교체 참고 시간. 누적 소비 유지, UI에서 자동 재시동하지 않음.

## 규정에서 뽑은 검증 과제

아래는 차량 구현 후의 시험 계획이다. 이번 자료조사에서 실차 시험을 완료한 것은 아니다. 전력 초과·차단·재출발 시나리오는 우선 기록 재생·저전압 시험 환경에서 검증하고, 실제 전장 시험 절차는 전장 담당자가 정한다.

| 시험 | 입력 / 관찰 | 판정할 내용 |
| --- | --- | --- |
| 빠른 과도 | 연속 초과와 500ms 평균 초과를 각각 합성, 불규칙 표본·누락 포함 | 현재 주기의 놓침을 재현. 정확한 시간 기준 계산과 기준 계측 오차를 보고. 공식 판정 일치 여부는 실제 미터로 별도 확인. |
| 최신성 | GPS·BMS 단절·부분 조회·재연결·SSE만 수신 | 캐시 값 정상 오인, 오래된 전류 적분, Range 확정 표시가 없는지. TTL은 실측 지터로 정하기. |
| 제동검사 속도 | 규정의 40km/h 기준·10m 제동 및 현장 계측과 비교 | 차량 표시–공식 속도 오차, 지연·필터 영향. 화면만 보고 제동검사 합격으로 처리하지 않음. [K02 제6조 p.2~3] |
| 교체·단계 | 공식 사인 확인, 중복 메시지, 3분·재출발 별도 시나리오 | 잘못된 교체 안내·시간 혼동·누적 초기화·자동 재시동 없음. 기산 시점은 현장 확인. |
| 전원·오프라인 | 서버 단절, 저장 실패, 전원 차단 후 부팅 | 전원 정상 시 로컬 지속. 전원 상실 시 마지막 확정 기록·누락 표시. 이전 오더를 현재 오더로 복원하지 않음. |

공식 속도계와 비교할 수 있는 제동검사 규정은 GPS 표시 검증의 현장 근거가 된다. 40km/h·10m 조건은 조직위원회가 현장 조건에 따라 변경할 수 있다. t측정→t수신→t표시를 나눠 평균 오차뿐 아니라 급가속·제동 중 지연을 남긴다. 필터 변화는 노이즈와 함께 비교한다.

핸드북 p.10의 제동검사 진입·운영 조건도 프로파일 자료로 남긴다. 교체·출발·종료의 이벤트 시각은 공식 기록과 팀 로그를 구분해 저장한다.


## 졸업연구 기여: 경기 판단의 오류를 줄이는가

권장 주제: “전기 경주차 계기판의 경기별 정보 구성과 데이터 유효성 표시가 규정 관련 상태 판단 및 내구 에너지 판단에 미치는 영향”. 규정은 과제를 정하는 근거로 사용하고, 새로운 화면이 위반·DNF를 실제 줄였다는 주장은 실험 근거가 있을 때만 한다.

| 질문 | 동일 로그의 과제 | 주요 지표 |
| --- | --- | --- |
| 정보 배치 효과 | 현재 UI와 제안 UI에서 속도·출력·소비 차이 판독 | 정확도·응답 시간·시선 이탈·TLX |
| 유효성 표시 효과 | 캐시·BMS 끊김·GPS 랩 누락·서버 단절 판단 | 오래된 값 오인·누락 탐지·부적절 행동 선택 |
| 교체·단계 효과 | 사인 전후, 재전송, 교체시간과 재출발시간 구분 | 잘못된 교체 판단·메시지 혼동·시간 해석 오류 |
| 완주 예산 효과 | 같은 잔여 에너지와 남은 랩에서 목표 대비 소비 판단 | 예산 오판·판독시간·추정 신뢰도 이해 |

기존 적용 분석의 2×2 비교(현재/제안 배치 × 유효성 유/무)를 활용하고 교체·예산 과제는 파일럿 규모에 맞게 단계적으로 추가한다. 작은 팀 표본은 사례연구로 보고하며 개인의 반복 시행을 독립 참여자 수로 세지 않는다. 공식 미터 검증과 운전자 UI 효과는 서로 다른 결과로 보고한다. [M02, G01]

### 보고서 평가와 연결할 산출물

설계 보고서에는 이전 차량과의 기술적 차이, 부품 선택·해석·검증을 남긴다. 비용 보고서에는 LCD·Pi·전원·케이스·브래킷·하네스·통신 장치 등 실제 사용 부품을 포함한다. 공개 사진 조사 자체와 실측 개선 결과를 구분하고 BOM·로그·UI 버전·규정 대응표를 함께 제출 자료로 정리한다. [K02 제3조 p.1]

검차 및 경기 프로파일은 버전, 출처, 공식 확인 근거를 저장한다. 연구용 화면의 가상 수치와 차량 측정값을 구분하여 다음 팀도 실험을 재현할 수 있게 한다.

지금의 결론은 테마 추가보다 규정에 맞는 계측·최신성·경기별 판단 정보가 먼저라는 것이다. 기존 상용차 사진과 모든 테마 구성 자료는 유지하고, 이 절을 대회 적용의 근거로 연결했다.

## 내구 에너지 판단을 단계적으로 추가하기

### 1. 먼저 검증된 누적 순소비를 연결

used_wh는 새로 만들어야 하는 계산이 아니다. 유효 전압·전류와 단조 시계 Δt로 적분하도록 검증하고, 방전 양수·회생 음수의 순소비로 이름을 명확히 한다. BMS가 오래됐거나 누락된 구간은 적분에서 구별하고 누락 시간·세션 경계를 함께 기록한다. [G01, G04]

### 2. 목표 대비 소비로 판단을 지원

후속 표시 후보는 유효 구간 ΔWh/Δkm 또는 유효 랩 ΔWh/lap이다. 순간 출력 kW와 구간 소비 Wh/km는 서로 다른 지표다. 정차·아주 짧은 거리·GPS 단절 구간의 비정상 분모를 제외하고, 예산과 비교할 때 같은 구간·같은 단위를 사용한다.

예산은 실험자가 정한 주행 목표 또는 측정 기반 경주 전략 입력이다. SOC×정격 용량만으로 남은 사용 가능 Wh를 확정하지 않는다. 사용 가능량·보존량·남은 거리/랩이 검증돼야 잔여 목표 예산을 계산할 수 있다. 준비 전에는 “예산 미설정/학습 중”을 표시한다.

| 표시 단계 | 필요 조건 | 검증 포인트 |
| --- | --- | --- |
| 누적 Wh | 유효 V·I·Δt, 세션·누락 기록 | 기준 적분 대비 오차, 중단·재시작·회생 처리 |
| 최근 Wh/km | 동일 구간 에너지·유효 GPS 거리 | GPS 흔들림·정차·속도 컷오프에 따른 편향 |

## 연구의 주장과 아직 확인해야 할 것

### 현재 자료로 주장할 수 있는 것

상용차에는 고정 정보·가변 콘텐츠·최소 표시·성능 중심 표시를 선택하는 다양한 설계가 있다. UNIMOTORS에는 큰 속도, BMS 경고, 로컬 기록, 누적 소비 계산을 활용할 기반이 있다. 주행 목적별 배치와 신호 유효성 피드백은 이를 발전시키는 비교 가능한 연구 가설이다.

### 졸업연구 주제의 권장 중심

“전기 내구 경주차 계기판에서 목적별 정보 배치와 데이터 유효성 피드백이 상태 판단에 미치는 영향”. 자료조사로 후보를 도출하고, 같은 로그 기반 UI 비교에서 효과를 검증한다. 새로운 외관 테마 자체를 연구 성과로 삼기보다 운전자의 판단을 개선한 근거를 남긴다.

이번 작업은 사진 수집·코드 정적 검토·설계 분석이다. 새로운 UI의 실차 구현·배포·센서 시험·효과 검증은 아직 수행하지 않았다.
